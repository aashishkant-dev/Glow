# Glow — Deep Audit (June 2026)

Scope: bugs, business-logic gaps, UX/notifications. Findings ranked by severity.
Status legend: 🔴 critical · 🟠 high · 🟡 medium · 🔵 low/polish.

---

## A. Business logic — money flow

### A1. 🔴 Payments are fictional (no charge, no capture, no refund)
`POST /bookings` computes `platformFee` + `providerPayout` and sets `paymentStatus:
PENDING`, but **never creates a Stripe PaymentIntent**. `complete` flips
`paymentStatus: RELEASED`; `cancel` flips `REFUNDED` — neither touches Stripe.
The `stripe@15.7.0` package is installed but unused. The whole
AUTHORIZED→PAID→RELEASED ledger exists only as enum values.
- **Impact:** Providers complete jobs and "earn" money no one paid. Withdraw pays out
  real-feeling balances against zero actual revenue.
- **Decision needed:** is this intentionally pre-launch mock (comments say "Stripe
  later")? If launching for real money, this is the #1 blocker.
- **Fix path:** create PaymentIntent (manual capture) on booking accept; capture
  on complete; refund on cancel; gate withdraw on real captured funds.

### A2. 🔴 Withdraw is not atomic / not idempotent → double payout
`POST /jobs/earnings/withdraw` reads `walletWithdrawn`, computes `available =
totalEarned - withdrawn`, then sets `walletWithdrawn = totalEarned`. Two
concurrent calls both read the old `withdrawn`, both compute the same
`available`, both respond "sent $X". Real money double-spend once Stripe is wired.
- **Fix:** wrap in a transaction with a conditional update (`where: { userId,
  walletWithdrawn: oldValue }`) or a DB-level lock / unique payout row per period.

### A3. 🟠 `accept` claim is not atomic → two Providers can claim one job
`provider.js:421-431` does `findFirst({ status: REQUESTED })` then `update({ where: {
id } })` — the update where-clause drops `status: REQUESTED`. Two Providers racing both
pass the check, both update; the second silently wins.
- **Fix:** `updateMany({ where: { id, status: 'REQUESTED' }, data: {...} })` and
  treat `count === 0` as "already claimed". (Postgres makes this atomic.)

## B. Business logic — lifecycle

### B1. 🟠 No Provider-side cancellation
Provider can `skip` only while REQUESTED (and once ACCEPTED, skip releases it back to
pool). But there's no clean "I can no longer make it" after ACCEPTED/ON_MY_WAY
that notifies the customer + reopens. `skip` does reopen on ACCEPTED/ON_MY_WAY but
is labeled/UX'd as decline, not cancel. Customer isn't clearly told.
- **Fix:** explicit Provider cancel with reason → reopen to pool + notify customer.

### B2. 🟡 `complete` has no sanity guards
STARTED→COMPLETED with no minimum elapsed time and no arrival check. A Provider can
`start` then `complete` one second later and "release" full payout. No customer
confirmation of completion.
- **Fix:** require `startedAt` + min duration (or customer confirm) before payout
  release; otherwise mark COMPLETED but hold payout.

### B3. 🟡 Accept push copy is wrong
On `accept` (status ACCEPTED) the customer push says "...has accepted your booking
and **is on the way!**" — but on-my-way is a separate later step. Misleading.
- **Fix:** "has accepted your booking" only; keep "on the way" for `on-my-way`.

### B4. 🔵 Single push token per user (multi-device gap)
`User.expoPushToken` is one field. Logging in on a second device overwrites it;
the first device goes silent. Fine for now; note for scale.

### B5. 🔵 Background jobs assume single instance
`requestTimeoutSweep` (setInterval) + request timeout run in-process. Multiple
Railway replicas would double-fire sweeps/pushes. Fine at 1 replica.

## C. Notifications — needs ONE coherent system

Today notifications come from **6 uncoordinated sources**, which is why
duplicates happen (the "3 notifications" bug was one instance):

1. Server Expo push (`pushTo`) — fires on every lifecycle event.
2. Socket event → `ChatUnreadContext` in-app banner + bell entry.
3. Socket event → `ProviderNavigator` handler (was: local notif + web notif — trimmed).
4. `ProviderNavigator.poll` (/jobs/nearby every 5s) → local + web notif for new jobs.
5. `ProviderNavigator.pollRequests` (every poll) → was banner + local + web (trimmed).
6. Web `document.title` flashing.

### C1. 🟠 No single notification policy
Each event can legitimately reach the user 2–3× (push + banner + local). The
recent fix patched the worst dup but the architecture still has overlapping
emitters with ad-hoc dedup (`notifiedReqIds`, `knownIds`).

**Proposed design — one dispatcher, foreground/background split:**
- **Single client helper** `notify(event)` that decides the channel:
  - App **foreground** → in-app banner ONLY (current `showBanner`). Never a local
    OS notification (it's redundant with the banner).
  - App **background** → rely on the **server Expo push** only. Kill client-side
    `scheduleLocal` for events the server already pushes.
- **Server is the single source of truth** for what's push-worthy. Client polls
  are a *fallback* for missed sockets — they should only raise the in-app banner,
  never a second OS notification.
- **Dedup by event id** (bookingId + type) in one place, not per-call-site.
- **Priority tiers:** dedicated request (high, banner+push) > status change
  (medium) > generic nearby job (low, list badge only — no push/banner).
- **Mute/quiet hours + per-type toggles** in profile (Providers get pinged a lot).

### C2. 🟡 Generic "nearby job" still pushes via server broadcast
`notifyNearbyProviders` pushes to all nearby Providers for every open booking. High volume →
notification fatigue. Client already treats nearby as low-priority (no banner).
Server should match: nearby = silent list update, only dedicated = push.

## D. UX / UI

### D1. 🟡 RatingModal error handling (FIXED this pass)
Was: failed submit hung the spinner forever. Now catches + shows error.

### D2. 🟡 "About you" row alignment (FIXED this pass)
Long bio squeezed the label / pushed the chevron. Left column locked.

### D3. 🟡 Inconsistent error surfacing across screens
Booking lifecycle onSubmit handlers (Tracking, BookingDetail, JobDetail) mostly
`await api...()` with no try/catch → a network error throws unhandled (stuck
button / silent fail). Pattern repeats. Audit all `onPress={async ...}` for
missing try/catch + user-visible error.

### D4. 🔵 Empty/loading/offline states uneven
Some lists have rich empty states (NearbyJobs), others none. No global offline
banner. Pull-to-refresh present in some lists, absent in others.

### D5. 🔵 Distance display inconsistency
`/jobs/nearby` now shows un-geocoded jobs without distance (good), but the card UI
should label them clearly ("Distance unavailable") rather than blank.
